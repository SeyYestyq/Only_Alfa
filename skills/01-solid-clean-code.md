# SOLID и чистый код (на примерах этого проекта)

## S — Single Responsibility: одна ответственность

Каждый модуль отвечает на один вопрос «почему он меняется».

- ✅ `scoring/risk_score.py` — только расчёт балла по факторам. `scoring/decision_engine.py` — только выбор коридора и контр-офферов. Смешать их в один `scoring.py` — нарушение: балл меняется по правилам рисковиков, решения — по продуктовой логике.
- ✅ React: `CashGapChart` только рисует график прогноза кассы; данные и форматирование — в хуке `useDashboard` и утилитах, не в компоненте.
- Признак нарушения: файл правится по трём разным поводам; класс называется `*Manager`, `*Helper`, `*Utils` и делает всё подряд.

## O — Open/Closed: расширение без модификации

Новое поведение — новым кодом, а не правкой рабочего.

- ✅ Новый триггер радара (например, TRG_SEASON) = новый класс обработчика + запись в реестре триггеров. Движок триггеров при этом не трогаем.
- ✅ Новый вид контр-оффера = новая стратегия в `decision/counter_offers/`, а не четвёртый `elif` в существующей функции.
- ❌ Запрещено: `if product == "overdraft": ... elif product == "vkl": ...` растущее по мере добавления продуктов — вместо этого реестр стратегий по `product_type`.

## L — Liskov Substitution: взаимозаменяемость

Любая реализация интерфейса работает везде, где ожидается интерфейс.

- ✅ Симуляторы реестров (`RegistryProvider`: ЕГРЮЛ, БКИ, ФССП, мультибанк) взаимозаменяемы: live-адаптер и seed-фолбэк возвращают одинаковую структуру и одинаково ведут себя при ошибках (исключение своего типа, не `None` и не «пустой успех»).
- ❌ Нарушение: наследник бросает исключение там, где базовый контракт обещает результат, или требует предобработки, о которой вызывающий не знает.

## I — Interface Segregation: маленькие интерфейсы

- ✅ Отдельные протоколы `ScoreCalculator`, `LimitPolicy`, `AuditWriter` вместо одного `BankService` с 20 методами.
- ✅ Фронтенд: компонент получает только нужные ему props, а не весь объект заявки «на всякий случай».
- Признак нарушения: реализация интерфейса, где половина методов — `raise NotImplementedError` или пустые заглушки.

## D — Dependency Inversion: зависимости от абстракций

- ✅ Сервис заявки получает репозиторий и калькулятор скоринга через конструктор (DI FastAPI / фабрика), а не создаёт их внутри. В тестах подставляются фейки без БД.
- ✅ Домен зависит от протоколов (`CompanyRepository`), инфраструктура зависит от домена — никогда наоборот.
- ❌ Запрещено: `import requests` / SQL-запросы / `os.environ` внутри доменной логики.

## Чистый код — рабочие правила

1. **Имена — документация.** `max_payment_rub`, а не `mp`. Функция-глагол: `calculate_risk_score`, а не `score`. Если имя требует комментария «что это» — переименуй.
2. **Функции короткие и одноуровневые.** Одно действие, один уровень абстракции внутри. Вложенность > 3 — выноси Guard Clauses / отдельные функции.
3. **Константы вместо магических чисел.** Пороги коридоров (650/520/450), веса факторов, 0.5 в формуле MaxPayment — только именованные константы в `domain/constants.py` со ссылкой на раздел BRD в комментарии.
4. **Ошибки — часть контракта.** Свои типы исключений домена (`InvalidTransition`, `AnomalyDetected`); на границе API они мапятся в HTTP-коды в одном месте. Никаких тихих `except Exception: pass`.
5. **Комментарии — только «почему».** «Что» видно из кода. Комментарий обязателен там, где правило взято из BRD (укажи раздел) или где решение неочевидно.
6. **Дублирование — с третьего раза.** Два похожих места оставляем; третье — повод выделить абстракцию. Преждевременные абстракции вреднее дублей.
7. **Форматирование — автоматом.** Python: ruff/black; TypeScript: prettier/eslint. Ручные споры о стиле запрещены — правит конфиг в репозитории.
8. **Перед сдачей — самопроверка запахов:** длинная функция? god-класс? feature envy (функция живёт не в своих данных)? shotgun surgery (одно изменение — правки в 6 файлах)? Если да — сначала рефакторинг отдельным коммитом `refactor:`.
