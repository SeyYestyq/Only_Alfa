# AGENTS.md — правила для ИИ-агентов и разработчиков

**Репозиторий:** Only_Alfa — «Умный кредитный кабинет предпринимателя» (хакатон «Альфа-Будущее»)
**Базовые документы:** BRD & SRS v3.0 и пакет ТЗ участникам (ТЗ-00 … ТЗ-05) — лежат в группе и в `docs/`. При конфликте этого файла с BRD приоритет у BRD.

Этот файл — закон для любого агента, который пишет или меняет код в репозитории. Прочитай его целиком до первой строки кода.

---

## 1. Стек и архитектура (фиксировано, не пересматривать)

- Frontend: React 18 + Vite + **TypeScript**. Backend: **Python 3.12 + FastAPI**, монолит. БД: **PostgreSQL 16**. Запуск: `docker compose up --build`.
- Backend — слоистая архитектура, зависимости только сверху вниз:
  `api/` (роуты, Pydantic-схемы) → `services/` (сценарии использования) → `domain/` (бизнес-логика: скоринг, State Machine, валидаторы) → `repositories/` (доступ к БД).
  Домен **не импортирует** FastAPI, SQLAlchemy и HTTP — только чистый Python и абстракции.
- Скоринг (RiskScore) и принятие решения (Decision Engine) — **разные модули**. State Machine заявки живёт только на бэкенде.
- Frontend не считает лимиты, баллы и статусы — только отображает ответы API.
- Никаких платных API, LLM и внешних сервисов в критическом пути. Внешние реестры — симуляторы с фолбэком `seed = hash(INN)`.

## 2. SOLID — обязательно (подробно: skills/01-solid-clean-code.md)

- **S** — один модуль/класс/компонент = одна ответственность. Файл > 300 строк — сигнал к декомпозиции.
- **O** — новые продукты, триггеры и контр-офферы добавляются новыми классами/записями в реестре, а не правками условий в существующих функциях.
- **L** — наследники и реализации интерфейсов взаимозаменяемы без сюрпризов для вызывающего кода.
- **I** — маленькие интерфейсы под конкретного потребителя; запрещено тянуть «толстый» интерфейс ради одного метода.
- **D** — зависимости через конструктор/DI и абстракции (протоколы/интерфейсы), а не `new`/прямые импорты конкретной реализации внутри бизнес-логики.

## 3. Чистый код (минимум, проверяется на ревью)

- Имена отвечают на вопросы «что это» и «зачем»: без `data2`, `tmp`, `func`. Булевы — с `is_/has_/can_`.
- Функция делает одно действие; > 40 строк или > 3 уровней вложенности — рефакторить до сдачи.
- Никаких магических чисел: веса скоринга, пороги коридоров, проценты — именованные константы в одном месте (`domain/constants.py`).
- Ошибки — явные исключения своих типов; запрещено глушить `except: pass` и возвращать `None` вместо ошибки без причины в контракте.
- Мёртвый код, закомментированные блоки и `print`-отладка в main не попадают.
- DRY — с третьего повторения, не раньше (не плодить абстракции ради одного случая). KISS и YAGNI выше «красивой архитектуры».

## 4. Фиксация изменений — каждое изменение след в гите (требование капитана)

- Работа только в ветке своего ТЗ: `feature/frontend-spa`, `feature/backend-core`, `feature/scoring-data`, `feature/smart-search`, `feature/qa-acceptance`. Прямые коммиты и пуши в `main` запрещены.
- **Conventional Commits:** `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:` + короткое «что и зачем». Один коммит = одно логическое изменение; «WIP» и «fix fix fix» не допускаются.
- Каждое изменение фиксируется трижды: **коммит → Pull Request с описанием → строка в CHANGELOG.md** (секция Unreleased, формат Keep a Changelog).
- PR описывает: что сделано, зачем, как проверено (команды/тесты), ссылка на пункт ТЗ/BRD.
- Агент в конце задачи **отчитывается человеку**: список изменённых файлов, что именно поменялось, чем проверил. Незакоммиченных изменений после задачи не остаётся.
- Секреты, токены и пароли в код и коммиты не попадают никогда (`.env` — в `.gitignore`).

## 5. Качество и тесты (подробно: skills/05-testing-quality.md)

- Доменная логика (скоринг, State Machine, валидатор аномалий, intent-парсер) покрывается юнит-тестами; контрольные значения — 5 демо-профилей BRD (баллы 815 / 610 / 760 / 495 / стоп-фактор).
- Перед PR: тесты зелёные, линтер и проверка типов без ошибок, `docker compose up --build` поднимает проект с нуля.
- Изменил контракт API → обнови `openapi.yaml` в том же PR и предупреди команду в группе.
- Definition of Done — по ТЗ-00: метрики успеха из ТЗ участника выполнены все.
